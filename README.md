# Curtain CRM — Design House

Внутренняя система учёта для мастерской по пошиву и установке штор:
веб-панель для руководства и мобильное приложение для персонала.
Заменяет Telegram-бота (`Nightcall7442/curtain-bot`).

## Структура

```
packages/shared   Перечисления, константы, чистые утилиты. Не зависит ни от чего.
packages/db       Схемы Drizzle, миграции, сид, хеширование паролей.
apps/api          tRPC-роутеры, сервисы, middleware.
apps/web          Веб-панель Next.js.
apps/mobile       Приложение Expo.
packages/config   Общий ESLint-пресет и базовый tsconfig.
```

Правило монорепозитория: роли, статусы и стадии живут **только** в
`packages/shared`. Строковых литералов вроде `'admin'` или `'sewing_done'`
в `apps/*` быть не должно.

## Требования

- Node.js **20.11+** (проверено на 24.x)
- pnpm 9 (`corepack enable`)
- PostgreSQL **16** — через Docker (`docker-compose.yml` в репозитории)
  либо нативной установкой

## Запуск локально

> **Про Windows PowerShell.** В версии 5.1 (та, что идёт с Windows по
> умолчанию) оператор `&&` **не поддерживается** — команды из bash-примеров
> вида `a && b` там падают с «Лексема "&&" не является допустимым
> разделителем операторов». Выполняйте команды по одной либо используйте
> `;` и `if ($?)`. Ниже каждый шаг дан в обоих вариантах.
> Проверить версию: `$PSVersionTable.PSVersion`.

**1. Зависимости**

```bash
corepack enable
pnpm install
```

**2. Переменные окружения**

```bash
# bash / git bash
cp .env.example .env
cp apps/api/.env.example apps/api/.env
```

```powershell
# PowerShell
Copy-Item .env.example .env
Copy-Item apps\api\.env.example apps\api\.env
```

В `apps/api/.env` обязательно замените `JWT_SECRET` — приложение не
запустится с секретом короче 32 символов. Сгенерировать:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

**3. PostgreSQL**

Нужен работающий PostgreSQL 16 на `localhost:5432`. Способ на выбор:

```bash
pnpm docker:up          # если установлен Docker (docker compose up -d)
```

Без Docker поставьте PostgreSQL нативно и создайте базу:

```powershell
winget install PostgreSQL.PostgreSQL.16
# затем, из папки установки PostgreSQL:
createdb -U postgres curtain_crm
```

В этом случае поправьте `DATABASE_URL` в `.env` под своего пользователя,
например `postgresql://postgres:ВАШ_ПАРОЛЬ@localhost:5432/curtain_crm`.

**4. Миграции и начальные данные**

```bash
pnpm db:migrate
pnpm db:seed
```

```powershell
# PowerShell одной строкой, с остановкой на первой ошибке
pnpm db:migrate; if ($?) { pnpm db:seed }
```

**5. Запуск**

```bash
pnpm dev                # все приложения через Turborepo
```

Отдельные приложения:

```bash
pnpm --filter @curtain-crm/api  dev     # http://localhost:3000/trpc
pnpm --filter @curtain-crm/web  dev     # http://localhost:3001
pnpm --filter @curtain-crm/mobile dev   # Expo
```

Проверка, что API поднялся:

```bash
curl http://localhost:3000/health
```

```powershell
Invoke-RestMethod http://localhost:3000/health
```

## Проверки

```bash
pnpm typecheck     # tsc --noEmit во всех шести пакетах
pnpm test          # 105 юнит-тестов
pnpm lint          # ESLint с проверкой типов
pnpm --filter @curtain-crm/web build   # сборка веб-панели
```

### Две отдельные темы

Веб-панель — тёмная (глубокий зелёно-синий фон, золотые акценты), мобильное
приложение — светлое с тёмно-бирюзовой шапкой. Это не рассогласование:
панелью пользуются в кабинете, приложением — в цехе и на объекте при дневном
свете, где тёмный экран нечитаем. Общими остаются данные и их подписи
(`@curtain-crm/shared`), а не оформление.

Палитра диаграмм проверена на различимость при нарушениях цветовосприятия;
исходные цвета этапов конвейера пришлось перебрать — соседние плитки
различались на ΔE 6.9, то есть выглядели одним цветом.

## Переменные окружения

Корневой `.env` — подключение к БД и параметры docker-compose.
`apps/api/.env` — всё остальное; полный список с комментариями в
`apps/api/.env.example`.

Ключевые:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение к PostgreSQL |
| `JWT_SECRET` | Подпись access-токенов, минимум 32 символа |
| `ACCESS_TOKEN_TTL_MINUTES` | Время жизни access-токена (15) |
| `REFRESH_TOKEN_TTL_DAYS` | Время жизни refresh-токена (30) |
| `CORS_ORIGINS` | Источники для веб-панели, через запятую |
| `STORAGE_DRIVER` | `disk` (разработка) или `s3` |
| `MAX_UPLOAD_SIZE_MB` | Предел размера фото и голосовых (15) |

## Как устроена бизнес-логика

- **Жизненный цикл заказа** задан одной таблицей `ORDER_TRANSITIONS`
  (`packages/shared/src/enums/orderStatus.enum.ts`): она определяет, какие
  переходы легальны, каким ролям они доступны, для каких обязателен
  комментарий и как подписать кнопку в интерфейсе.
- **Статус меняется только** через `changeOrderStatus()`
  (`apps/api/src/services/orderWorkflow.service.ts`). Роутеры не пишут
  `orders.status` напрямую: иначе переход мог бы состояться без записи
  в историю и без уведомлений.
- **`order_status_history` только пополняется.** Откат на предыдущий этап —
  это новая строка с обязательной причиной, а не правка старой.
- **Архив — это фильтр**, а не отдельная таблица: выполненные и отменённые
  заказы остаются в `orders`.
- **Расчёт зарплаты** — чистые функции без побочных эффектов, по одной на тип
  схемы (`apps/api/src/services/payroll.service.ts`), покрыты тестами.
  Утверждённые периоды не пересчитываются: в записи хранится снимок
  параметров схемы.
- **Права проверяются в tRPC-middleware** (`roleGuard`), а не в интерфейсе.
  Скрытая кнопка — удобство, граница доверия — процедура.

## Известные ограничения

Всё перечисленное ниже — сознательно НЕ реализованное, а не забытое.
В интерфейсе такие разделы показывают, чего именно не хватает в системе,
вместо правдоподобных выдуманных цифр: экран с выдуманными данными
невозможно отличить от рабочего, и по нему начинают принимать решения.

- **S3-драйвер хранилища** — заглушка, которая явно падает с понятной
  ошибкой. Рабочий драйвер для разработки — `disk`.
- **Клиентские SMS и пуш-уведомления** не реализованы. Модель их не
  блокирует: достаточно добавить значение в `NOTIFICATION_TYPES` и канал
  доставки в `notifications.service.ts`.
- **Роль `smm`** зарезервирована в перечислении, `smm.router.ts` содержит
  только `ping`, в расчёте зарплаты роль не участвует.
- **Разделы «Клиенты», «Продажи», «Склад тканей», «Обучение»** — заглушки:
  под них нет модели данных. Каждая страница перечисляет, что нужно завести,
  чтобы раздел заработал.
- **«Финансы»** перенаправляет в «Отчёты»: те же цифры под двумя названиями
  быстро превращаются в два расходящихся источника правды.
- **Задачи сотрудника** как отдельная сущность отсутствуют. «Мои задачи»
  в приложении — это заказы, по которым сотрудник может сделать следующий
  шаг; список действий берётся из той же таблицы переходов, что и кнопки.
- **Конверсия продавца, процент качества, остатки ткани** не считаются:
  нет учёта обращений, оценок качества и складских движений.
- **Выгрузка в Excel** не реализована.
- **Перерывы внутри смены** не учитываются — по требованию заказчика смена
  представляет собой один непрерывный блок.

## Демонстрационные данные

Сид создаёт минимум для работы. Чтобы увидеть интерфейс на реальном объёме:

```bash
pnpm --filter @curtain-crm/api run demo
```

Два филиала, 21 сотрудник по всем ролям и подразделениям, ~66 заказов во
всех статусах, смены за полтора месяца, закупки и расчёты зарплаты за два
периода. Демо-сотрудники входят по паролю `Demo2026!`.

Заказы прогоняются по жизненному циклу **через реальные сервисы**, а не
вставками в БД, поэтому история статусов, уведомления и автоназначение ОТК
получаются настоящими. Повторный запуск сначала удаляет данные предыдущего.

> Скрипт заметно меняет содержимое базы — не запускайте его на проде.

## Интеграционная проверка

Юнит-тесты покрывают чистые функции, но не SQL. Всё, что можно проверить
только на живой базе, вынесено в отдельный скрипт:

```bash
pnpm --filter @curtain-crm/api run smoke
```

29 проверок: генерируемые колонки (`order_number`, `remaining_payment`),
check-констрейнты, частичный уникальный индекс «одна открытая смена»,
полный жизненный цикл заказа через `changeOrderStatus` (включая отказы —
нелегальный переход, чужой заказ, откат без причины), оконный расчёт часов
и агрегаты отчётов (`count(*) filter`, `bool_or`, `date_trunc`).

Скрипт создаёт свои данные с префиксом `SMOKE` и убирает их за собой,
поэтому его можно запускать на рабочей базе и повторно.

> Именно эта проверка нашла баг, невидимый для типов и юнит-тестов:
> в выражении `$1::timestamptz` PostgreSQL описывает параметр как `text`,
> и драйвер падал, получив объект `Date`. Подробности — в комментарии
> к `sqlTimestamp()` в `apps/api/src/services/shifts.service.ts`.

## Эксплуатация

### Развёртывание

Один сервер, четыре контейнера: база, API, панель и обратный прокси
с автоматическим HTTPS. Наружу торчит только прокси.

```bash
cp .env.production.example .env.production
# заполнить DOMAIN, ACME_EMAIL, POSTGRES_PASSWORD, JWT_SECRET
chmod 600 .env.production

docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build

# первый и единственный раз — схема и учётная запись директора
docker compose -f docker-compose.prod.yml --env-file .env.production \
  exec api pnpm db:migrate
docker compose -f docker-compose.prod.yml --env-file .env.production \
  exec api pnpm db:seed
```

Условие одно: домен из `DOMAIN` указывает A-записью на этот сервер, порты
80 и 443 открыты. Сертификат Let's Encrypt Caddy получит сам при первом
запуске и будет продлевать дальше — ни certbot, ни заданий в cron не нужно.

**Пароль директора сменить сразу после первого входа.**

#### Почему так

*Панель и API на одном домене.* Прокси разводит `/trpc` и `/files` на API,
остальное — на панель. Адрес API в бандле относительный (`/trpc`), поэтому
образ панели не привязан к домену и пересобирать его под каждое окружение
не нужно. Побочная выгода: запросы становятся однодоменными, и CORS в проде
не участвует вовсе.

*Один экземпляр каждого сервиса.* Ограничитель попыток входа хранит счётчики
в памяти процесса — при двух экземплярах API они считали бы порознь. Для
мастерской с двумя десятками сотрудников это соразмерно; при переходе
на несколько экземпляров счётчики нужно вынести в Redis (менять придётся
только `loginThrottle.service.ts`).

*Том `storage` обязателен* при `STORAGE_DRIVER=disk`: без него фотографии
заказов и голосовые комментарии исчезнут при первом же пересоздании
контейнера, а в базе останутся ключи на несуществующие файлы.

*`TRUST_PROXY_HEADERS=true`* — за прокси адрес клиента приходит заголовком.
Без этого ограничитель обращений считал бы весь трафик как одного клиента.
При прямом подключении, наоборот, заголовку доверять нельзя — он подделывается.

*Образы одностадийные.* pnpm раскладывает зависимости символическими ссылками,
и копирование `node_modules` между стадиями сборки их ломает. Образ выходит
крупнее, зато собирается тем же способом, каким проект работает локально.

*API запускается через `tsx`*, как и локально: пакеты монорепозитория
подключены исходниками, и компиляция API в JavaScript потребовала бы сборки
ещё и для `shared` с `db`. Отдельная задача; выигрыш будет во времени
старта, а не в скорости работы.

#### Обновление

```bash
git pull
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
docker compose -f docker-compose.prod.yml --env-file .env.production exec api pnpm db:migrate
```

#### Что проверено, а что нет

Топология проверена целиком, но **без Docker**: API в режиме `production`,
собранная панель и обратный прокси были подняты локально по той же схеме,
что задаёт `Caddyfile`. Через прокси прошли вход, дашборд, журнал аудита,
загрузка файла и его чтение по подписанной ссылке; все запросы шли
однодоменно, ответы об ошибках в проде приходят без стека.

**Сами образы не собирались** — Docker на машине разработчика отсутствует.
Первый `docker compose build` стоит выполнить до того, как на сервер
понадобится выкатываться срочно.

### Резервные копии

```bash
pnpm --filter @curtain-crm/api backup
```

Сохраняются два набора данных — по отдельности они бесполезны: дамп базы
(`pg_dump -Fc` — сжатый, восстанавливается выборочно) и каталог файлового
хранилища при `STORAGE_DRIVER=disk`. В базе от фотографий и голосовых
комментариев остаются только ключи — без файлов галерея заказа пуста.
При `STORAGE_DRIVER=s3` файлы пропускаются: у бакета для этого есть
версионирование и правила жизненного цикла.

Настройки — переменными окружения:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `BACKUP_DIR` | `./backups` | Куда складывать |
| `BACKUP_KEEP` | `14` | Сколько копий хранить; старые удаляются ПОСЛЕ успешного создания новой |
| `PG_DUMP_PATH` | автопоиск | Путь к `pg_dump`, если его нет в `PATH` — на Windows установщик его туда не добавляет |

Пароль передаётся `pg_dump` через `PGPASSWORD`, а не в строке подключения:
аргументы командной строки видны в списке процессов любому пользователю машины.

Команда восстановления печатается в конце каждого прогона, чтобы её не
пришлось вспоминать в тот момент, когда она понадобится:

```bash
createdb curtain_crm_restored
pg_restore --dbname=curtain_crm_restored --no-owner --clean --if-exists .../database.dump
# и скопировать .../storage в STORAGE_DISK_PATH
```

> **Учение по восстановлению обязательно, и его ещё не проводили.** Дамп
> проверен `pg_restore --list` — 20 таблиц, 20 блоков данных, 61 индекс,
> 55 ограничений, 13 enum-типов, — но это проверка целостности файла, а не
> восстановления. Полный прогон требует пользователя с правом `CREATEDB`;
> у роли `curtain` его нет, и на рабочей базе такое учение проводить нельзя.
> Бэкап, который ни разу не разворачивали, — это надежда, а не бэкап.

### Расписание

Скрипт запускается извне — своего планировщика в системе нет намеренно.
Ежедневно, ночью:

```cron
0 3 * * * cd /srv/curtain-crm && BACKUP_DIR=/var/backups/curtain pnpm --filter @curtain-crm/api backup >> /var/log/curtain-backup.log 2>&1
```

Копии должны уезжать с той же машины, где стоит база: диск отказывает
целиком, вместе с копиями на нём.

### Уборка осиротевших файлов

```bash
pnpm --filter @curtain-crm/api gc            # только показать
pnpm --filter @curtain-crm/api gc -- --apply # удалить
```

Сверяет каталог хранилища с колонками, где лежат ключи. Файлы моложе часа
пропускает намеренно: загрузка кладёт файл раньше записи в БД, и без запаса
уборщик снёс бы то, что грузится прямо сейчас.

### Непрерывная интеграция

`.github/workflows/ci.yml` — три работы на каждый push:

| Работа | Что делает |
|---|---|
| `checks` | типы, стиль, юнит-тесты, проверка S3-драйвера, сборка веб-панели |
| `integration` | поднимает PostgreSQL 16, накатывает миграции С НУЛЯ и гоняет смоук |
| `mobile` | собирает бандл приложения и проверяет зависимости `expo-doctor` |

Мобильная работа выделена не для порядка: ни `tsc`, ни ESLint не видят
проблем разрешения модулей — Metro резолвит по своим правилам. Приложение
однажды уже не собиралось из-за ненайденного `@babel/runtime`, и заметить
это можно было только сборкой.

## Что можно делать из интерфейса

Все 46 мутаций API подключены к экранам:

| Раздел | Действия |
|---|---|
| Заказы | создать заказ с позициями, править, менять цену, назначать мастера / швею / ОТК / установщика, двигать по статусам с откатами, отменять с причиной, комментировать, вести закупки, загружать фото по стадиям |
| Сотрудники | заводить, править анкету, выдавать и отзывать роли, привязывать филиалы, сбрасывать пароль, принимать и увольнять |
| Табель | заводить смену задним числом, править время, удалять ошибочную — всё с обязательной причиной и уведомлением сотруднику |
| Зарплата | считать период, настраивать схему начисления по роли, утверждать, отмечать выплату |
| Настройки | филиалы и радиус отметки, справочники характеристик, каталог закупки, смена пароля, выход со всех устройств |
| Мобильное | вход, чек-ин и чек-аут по геолокации, свои заказы и задачи, переходы статусов, комментарии, **фотофиксация с камеры** |

Загрузка фото стадии «После установки» автоматически закрывает заказ —
и в панели, и в приложении, с предупреждением перед отправкой.
