# Архитектура

Документ объясняет, **почему** система устроена так, а не что в ней есть.
Перечень процедур — в [API.md](./API.md), правила предметной области —
в [BUSINESS_LOGIC.md](./BUSINESS_LOGIC.md).

## Состав

```
apps/api        tRPC поверх Hono — единственный источник бизнес-логики
apps/web        Next.js 15, App Router — панель руководства и офиса
apps/mobile     Expo (React Native) — приложение цеха и объекта
packages/shared перечисления, константы, чистые утилиты
packages/db     схема Drizzle, миграции, подключение, сид
packages/config общие конфигурации ESLint и TypeScript
```

Пакеты подключаются **исходниками**, без шага сборки: `"main": "./src/index.ts"`.
Отдельная сборка `shared` и `db` заставила бы пересобирать их при каждой
правке и породила бы вопрос «какая версия сейчас у клиента». Плата —
Next транспилирует `@curtain-crm/shared` сам (`transpilePackages`), а API
работает через `tsx`, в том числе в контейнере.

## Направление зависимостей

```
shared ← db ← api ← web
                 ↖ mobile
```

Строго в одну сторону, циклов нет. `shared` не знает ни про Drizzle, ни про
tRPC, ни про React — поэтому годится и серверу, и React Native. `db` знает
только про `shared`.

Внутри API порядок такой же односторонний:

```
trpc.ts → middleware/ → routers/
              ↘ services/
```

## Контракт между сервером и клиентами

Контракт — это **тип** `AppRouter`, а не документация. Клиенты импортируют
его через `import type`, поэтому он стирается компилятором и ни Hono, ни
Drizzle, ни драйвер PostgreSQL в браузерный бандл не попадают.

Практическое следствие: переименование процедуры или изменение её входных
данных **ломает сборку клиента**, а не продакшен при первом клике.

Транспорт — `superjson`. Без него `Date` в ответах превращался бы в строку,
и каждому клиенту пришлось бы вручную разбирать даты смен и дедлайнов.

## Где живут инварианты

Ключевое решение: **правила, нарушение которых недопустимо, вынесены в БД**,
а не остались проверками в коде. Проверка в приложении защищает от ошибки
в приложении; ограничение в базе защищает ещё и от миграции, скрипта
и ручного `UPDATE`.

| Инвариант | Чем обеспечен |
|---|---|
| Номер заказа `DH-000123` | генерируемая колонка `'DH-' \|\| lpad(id::text, 6, '0')` |
| Остаток оплаты | генерируемая колонка `work_price - deposit` |
| Сумма закупки | генерируемая колонка в `purchases` |
| Одна открытая смена на сотрудника | частичный уникальный индекс `where ended_at is null` |
| Отмена заказа только с причиной | check-констрейнт |
| Голосовой комментарий без файла невозможен | check-констрейнт |
| Поля схемы оплаты соответствуют её типу | check-констрейнт `payroll_schemes_fields_match_type` |

Всего 31 check-констрейнт, 35 внешних ключей, 80 индексов, 3 вычисляемые
колонки.

Генерируемая колонка для номера заказа выбрана вместо последовательности
намеренно: она выводится из `id` и потому не может разойтись с ним
при параллельном создании заказов.

### Политики удаления

`onDelete: 'restrict'` у всех колонок «кто сделал» (`orders.created_by`,
`audit_log.actor_id`, `purchases.created_by`, …): сотрудников система
не удаляет вовсе — увольнение это `setActive(false)`, — и запрет
на уровне БД подкрепляет это правило.

`onDelete: 'cascade'` там, где запись не имеет смысла в отрыве от родителя:
позиции заказа, фотографии, комментарии, история статусов, уведомления.

`ON UPDATE` не задан ни у одного ключа, и это решение, а не упущение: все
цели ссылок — суррогатные `serial`, которые не меняются.

## Единственная точка смены статуса

`orders.status` пишется **только** функцией `changeOrderStatus()` в
`orderWorkflow.service.ts`. Ни один роутер не трогает колонку напрямую.

Иначе переход мог бы состояться без записи в `order_status_history`,
без проверки прав и без уведомлений — и восстановить, что произошло
с заказом, стало бы невозможно.

Заказ читается через `SELECT ... FOR UPDATE`: без блокировки два
параллельных перехода прочитали бы один и тот же исходный статус, и оба
записали бы свой — в истории появился бы невозможный переход.

## Права доступа

Пять уровней, каждый — middleware поверх предыдущего:

```
baseProcedure          публичный (login, refresh, health)
protectedProcedure     любой вошедший
  + участие в заказе   assertCanAccessOrder
managementProcedure    директор и админ
ceoProcedure           только директор
```

Интерфейс скрывает кнопки и пункты меню, но это **исключительно удобство**.
Граница доверия — процедура tRPC. Открыть адрес напрямую бесполезно:
страница получит `FORBIDDEN` от API.

Журнал аудита доступен только директору намеренно: он показывает в том числе
действия администратора, и проверяющий с проверяемым совпадать не должны.

## Аутентификация

Пара токенов: access живёт 15 минут, refresh — 30 дней и **ротируется**
при каждом обновлении.

Предъявление уже отозванного refresh-токена трактуется как кража: злоумышленник
использует украденную копию после того, как настоящий клиент её обновил.
В этом случае гасятся **все** сессии сотрудника.

> Отзыв выполняется отдельной транзакцией ПОСЛЕ выхода из основной. Раньше он
> шёл внутри транзакции, которая следом откатывалась брошенным исключением:
> система сообщала «все устройства отключены», а украденный токен оставался
> рабочим ещё 30 дней. В SQL-логе `UPDATE` при этом был виден.

Мобильное приложение хранит токены в Keychain / EncryptedSharedPreferences.
Веб-панель — в `localStorage`; это осознанный компромисс, описанный
в `apps/web/src/lib/trpc.ts`, и он ещё подлежит пересмотру.

Вход ограничен: пять неудач подряд по одному номеру закрывают его на 15 минут,
плюс потолок обращений к `auth.*` с одного адреса. Счётчики живут в памяти
процесса — при нескольких экземплярах API их нужно вынести в общее хранилище,
менять придётся только `loginThrottle.service.ts`.

## Файловое хранилище

Абстракция намеренно узкая: `upload` / `getUrl` / `delete` / `exists`.

- `DiskStorageDriver` — файлы на диске, ссылки подписываются HMAC и живут час;
- `S3StorageDriver` — AWS и совместимые (MinIO, Yandex Object Storage, R2),
  ссылки подписывает сам S3.

В БД хранится только ключ объекта. Публичный адрес получают через `getUrl()`
на каждый запрос заново — поэтому истёкшая ссылка чинится перезагрузкой
страницы, а не миграцией данных.

Токен при раздаче файлов проверить нельзя: `<img src>` и `<audio src>`
не отправляют заголовок `Authorization`. Отсюда подписанные адреса.

Файл кладётся в хранилище **до** записи в БД: при сбое остаётся объект без
ссылки — это дешевле, чем строка в БД без файла, на которой ломается галерея.
Осиротевшие объекты убирает `pnpm --filter @curtain-crm/api gc`.

## Развёртывание

Один сервер, четыре контейнера: PostgreSQL, API, панель, обратный прокси
с автоматическим HTTPS. Наружу торчит только прокси.

Панель и API живут на одном домене: прокси разводит `/trpc` и `/files`
на API, остальное — на панель. Адрес API в бандле **относительный**, поэтому
образ не привязан к домену, а CORS в проде не участвует вовсе.

Экземпляр каждого сервиса один. Для мастерской с двумя десятками сотрудников
это соразмерно, а не упрощение: ограничитель попыток входа хранит счётчики
в памяти процесса.

Подробности — в разделе «Эксплуатация» корневого `README.md`.

## Проверки

| Уровень | Что ловит |
|---|---|
| `tsc --noEmit` | контракт между сервером и клиентами |
| ESLint с типами | `any`, небезопасные операции, мёртвый код |
| Юнит-тесты (105) | чистые функции: переходы, деньги, размеры, расчёт зарплаты |
| Смоук на живой БД (35) | всё, что живёт в SQL: генерируемые колонки, констрейнты, частичные индексы, блокировки |
| `s3:check` (13) | драйвер хранилища против локального S3-совместимого сервера |
| Сборка мобильного бандла | разрешение модулей, которого не видят ни типы, ни линтер |
