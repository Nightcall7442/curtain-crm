# Бизнес-логика

Правила предметной области: жизненный цикл заказа, роли, смены, зарплата.
Устройство системы — в [ARCHITECTURE.md](./ARCHITECTURE.md), перечень
процедур — в [API.md](./API.md).

Источник правды для перечислений — `packages/shared`. Ни один литерал роли
или статуса не написан в приложениях руками.

## Роли

Роль — не поле сотрудника, а связь many-to-many: мастер-замерщик может быть
одновременно швеёй, и права складываются.

| Роль | Что делает |
|---|---|
| `ceo` | Всё. Единственный, кто управляет ролями и читает журнал аудита |
| `admin` | Ведёт заказы, назначает исполнителей, корректирует смены |
| `seller` | Заводит заказы |
| `master` | Замер |
| `sewer` | Пошив |
| `qc` | Контроль качества |
| `installer` | Установка |
| `smm` | Роль заведена, **задачи заказчиком не определены** |

Ролями управляет **исключительно директор**, в том числе своими —
требование заказчика. Администратор ролями не управляет.

Сотрудники не удаляются: увольнение — `setActive(false)`, которое
дополнительно завершает все его сессии.

## Жизненный цикл заказа

17 статусов. Прямой путь:

```
new → pending_admin_review → measurement_assigned → measurement_done
    → pending_sewing_assignment → sewing_in_progress → sewing_done
    → pending_qc → qc_passed → pending_installation_assignment
    → installation_assigned → installation_in_progress → installation_done
    → completed
```

Побочные ветки: `rejected_to_ceo` (админ отклонил, решает директор),
`qc_failed` (брак), `cancelled` (отмена из любого незакрытого статуса).

Замер — **необязательный шаг**: админ вправе передать заказ сразу в пошив.

Переходы описаны таблицей `ORDER_TRANSITIONS`; у каждого указаны роли,
которым он разрешён, вид (`forward` / `rollback` / `reject` / `cancel`)
и подпись кнопки. Клиенты рисуют кнопки строго по ответу
`orders.availableTransitions`, а не по собственным догадкам о правах.

### Что проверяется при переходе

По порядку, до записи:

1. **Доступ к заказу.** Участник — или сотрудник с ролью этапа, пока
   исполнитель не назначен (общий пул).
2. **Легальность перехода** по таблице.
3. **Роль** — разрешён ли этот конкретный переход этой роли.
4. **Принадлежность этапа** — заказ в пошиве принадлежит назначенной швее,
   а не любой швее цеха. Руководство не ограничено.
5. **Обязательный комментарий** для откатов, отклонений и отмен.
6. **Наличие исполнителя** там, где без него статус бессмыслен.

Первая проверка идёт первой не случайно: сообщения об ошибках ниже называют
статус и номер заказа, и без неё перебором `id` можно было вычитать
состояние чужих заказов — мутация не проходила, но данные утекали.

### Автозакрытие

Загрузка фото стадии **«После установки»** переводит заказ в `completed`
автоматически, при необходимости через `installation_done`. Подтверждение
клиента не требуется.

Системный переход снимает проверку **роли** (закрыть заказ вручную вправе
админ или директор, а автозакрытие запускает установщик), но **не** проверку
принадлежности этапа: чужую установку закрыть нельзя.

### История

Каждый переход пишется в `order_status_history`: откуда, куда, кто, когда,
комментарий. Таблица append-only.

Сортировка — по времени **и по `id`**. Второй ключ обязателен: `created_at`
по умолчанию `now()`, а это время начала транзакции, и записи одной
транзакции делят метку. Без `id` пара «назначен установщик» и «установка
идёт» могла встать в обратном порядке — а историей разбирают спор с клиентом.

## Видимость заказов

Рядовой сотрудник видит только заказы, где он участвует: создал, назначен
мастером, швеёй, ОТК или установщиком. Руководство видит все.

Фильтр применяется в SQL, а не в приложении: иначе чужие заказы выгружались
бы из базы и отсеивались уже после.

## Смены

Чек-ин по геолокации: координаты проверяются на попадание в радиус филиала,
расстояние сохраняется. Открытая смена может быть только одна — это
гарантирует частичный уникальный индекс, а не проверка в коде.

Смена — один непрерывный блок без учёта перерывов.

Часы считаются оконным выражением с обрезкой по границам месяца: ночная
смена с 31-го на 1-е иначе целиком попала бы в один из двух месяцев.
Открытые смены в расчёт не идут — их длительность ещё не определена.

Руководство может скорректировать смену вручную, обязательно с причиной;
корректировка попадает в журнал аудита.

## Зарплата

Схема привязана к **роли**, а не к сотруднику: у мастера-замерщика, который
ещё и швея, начисление идёт по двум схемам. У схемы есть `effective_from`,
поэтому изменение ставки не переписывает прошлые расчёты.

### Четыре типа

| Тип | Формула | Обязательные поля |
|---|---|---|
| `fixed` | оклад за период целиком | `baseAmount` |
| `hourly` | ставка × отработанные часы | `rate` |
| `kpi` | оклад + премия × min(1, факт / план) | `baseAmount`, `rate`, `kpiTarget` |
| `commission` | процент от суммы закрытых заказов | `commissionPercent` |

Соответствие полей типу проверяет check-констрейнт в БД, а не только код.

### Допущения, требующие согласования

Записаны в шапке `payroll.service.ts` и **с заказчиком не согласованы**:

1. **KPI** — число заказов, *закрытых* за период с участием сотрудника
   в этой роли. Не созданных и не начатых.
2. **Премия не растёт свыше 100 % плана.** Сделал 150 % — получил как
   за 100 % (`Math.min(1, achievement)`).
3. **База для процента — выручка** (`work_price`), а не маржа за вычетом
   закупок.
4. У админа и директора KPI считается по **всем** закрытым заказам компании.
5. **SMM в расчёте не участвует** — функционал роли не определён.

Пункты 2 и 3 — про разные деньги, и решение здесь за заказчиком.

### Порядок

```
черновик → утверждён → выплачен
```

Пересчёт возможен только пока запись — черновик. При утверждении сумма
фиксируется, а в записи сохраняется **снимок схемы**: изменение ставки
задним числом не перепишет уже утверждённый расчёт.

## Деньги

Хранятся в минорных единицах (тийинах) целыми числами. Дробная арифметика
на деньгах не применяется нигде.

**Одна книга проводок** (`payments`) — единственный источник правды о
деньгах (см. [ADR-0001](./adr/0001-one-money-ledger.md) и глоссарий в
[CONTEXT.md](../CONTEXT.md)). Одна строка — одно движение, вид задаёт знак:

| Вид | Что это | Знак |
|---|---|---|
| `order_deposit`, `order_balance`, `ready_made`, `other` | приход от клиента | + |
| `collection` | инкассация: наличные с рук в кассу | перекладывание |
| `payroll` | выплата сотруднику по расчёту | − |
| `refund` | возврат клиенту | − |

Всё производное считается только из книги:

- **Оплачено по заказу** = приходы − возвраты. Колонка `orders.paid_amount`
  — кэш, который поддерживает триггер базы на каждую проводку; приложение её
  не пишет. Остаток = `work_price − paid_amount` (генерируемая колонка,
  может быть отрицательным — переплата). Возврат больше оплаченного база
  отвергает.
- **На руках** у сотрудника = наличные приходы − инкассации − наличные
  возвраты. У руководства «на руках» нет: принятое им — сразу касса.
- **В кассе** (наличные, накопленным итогом с первого движения через книгу)
  = инкассации + наличные руководства − выплаты − закупки − наличные
  возвраты руководства. Закупки — документы, не проводки: касса читает их
  как расход напрямую.
- **На счёте** = безналичные приходы − безналичные возвраты, по способам
  (карта, QR, Click).

Способы оплаты: наличные, карта (терминал), QR, Click. «Предоплата» как
поле заказа больше не существует — первая оплата при приёме заказа это
просто первая проводка. Руководство не правит «оплачено» числом: только
«Принять оплату» или «Возврат».

Номер заказа `DH-000123` / `TDH-000123` — генерируемая колонка из `id`.

**Кто видит деньги клиента** (стоимость, оплачено, остаток): руководство
и продавец. Цеху — швее, мастеру, ОТК, установщику, карнизчику — эти поля
приходят `null` из API (`maskStageFees` в `orders.router.ts`), а не
прячутся в интерфейсе; установщик своего заказа видит их — он берёт
остаток. Расценки этапов — только руководству и исполнителю своего этапа.

### Скидки

Скидку дают при приёме — на заказ, на готовые шторы с витрины и на кассе
(чек по кодам склада) — суммой или процентом, с обязательной причиной. `orders.work_price` хранит цену **уже со
скидкой**, `discount_amount` — сколько сняли, `discount_reason` — за что.
Остаток, оплаты и процент продавца считаются от цены со скидкой, как раньше;
цена до скидки — `work_price + discount_amount`. Руководство может поправить
скидку в заказе (`orders.setPrice`). У чека витрины (`retail_sales`) то же
самое: строки остаются по цене с бирки, скидка идёт сверху, а в кассу
попадает сумма за вычетом скидки. Скидки видны в заказе, в кассе дня
(«Скидки за день») и в отчёте `reports.discounts` — заказы и чеки в одной
таблице: кто, кому, сколько и за что, с выгрузкой в Excel.

## Себестоимость и маржа

Себестоимость заказа — сумма закупок по нему. Маржа считается от суммы работ.

Участник заказа видит **только закупки**: сколько потрачено на его заказ —
рабочая информация. Выручка, маржа и рентабельность приходят `null` всем,
кроме руководства.

## Качество работы

Отдельной оценки качества в системе нет. Единственный объективный след —
**возвраты на переделку**, и качество считается по ним:

| Роль | Что считается браком |
|---|---|
| Швея | заказ вернули с контроля (`→ qc_failed`) |
| Мастер | заказ отправили на *повторный* замер, то есть в `measurement_assigned` откатом с более позднего этапа |
| Установщик | установку вернули на доработку (`installation_done → installation_in_progress`) |

Показатель — доля заказов сотрудника без такого возврата.

## Фотофиксация

Восемь стадий: замер, ткань, раскрой, пошив, контроль, до установки,
после установки, общее. У каждой свой список ролей-загрузчиков; директор
и админ включены во все — руководству регулярно приходится закрывать
пробелы за сотрудниками.

Стадия «общее» свободна: приложить фото может любой участник заказа.

## Уведомления

Сотрудник получает уведомление **только о своих задачах**: заказ назначен
ему, сменился статус этапа, за который он отвечает, скорректирована его
смена, добавлен комментарий к его заказу.

Рассылок «всем подряд» нет намеренно: лента, в которой 90 % чужого,
перестаёт читаться.

## Справочники

Модели штор, материалы, опции материала, цвета, карнизы, тюль, сачак,
аксессуары — таблица `catalog_items`, редактируется руководством через
интерфейс. Начальные значения задаёт сид, но код с ними **не сравнивается**:
справочник живой.

## Три независимых учёта

Владелец развёл деньги на три вещи, которые друг с другом не связаны:

1. **Касса** — наличные от продаж: инкассация плюс принятое руководством,
   минус закупки и возвраты. Дневная карточка показывает только день
   (принято, сдано, на руках, скидки, ушло за день); накопленные остатки —
   отдельным блоком «Итого за всё время».
2. **Терминальные чеки** — записи о пробитых фискальных чеках (вид проводки
   `terminal_check`): фото и сумма, норма три в день. В кассу и на счёт не
   попадают, в «Приход по источникам» не входят.
3. **Зарплата** — выплаты сотрудникам. Видны отдельной строкой («Выплачено
   зарплаты»), но из остатка кассы **не вычитаются**.

## Терминальные чеки

Обязанность продавцов, заданная владельцем: за день пробить на платёжном
терминале не меньше **3 чеков** (`TERMINAL_CHECKS_DAILY_TARGET`) — на всех
продавцов, не на каждого.

Чек — не отдельная сущность, а **приход по карте в книге проводок** с фото
чека. Поэтому «пробито сегодня» и «принято картой» — одно число: карта,
принятая по заказу продавцом или установщиком, тоже идёт в норму.

- Пробил один — остальным продавцам приходит уведомление «сегодня 2 из 3,
  остался 1»; в 10:00 и 15:00, пока цель не закрыта, — напоминание.
- Руководство видит чеки за день на странице «Касса», архив — с фото.

## Дисциплина

Система ответственности из презентации владельца: **факт → балл → действие**.
Менеджер фиксирует факт и выбирает категорию; балл даёт таблица в
`packages/shared/src/constants/discipline.ts`, одна для всех.

| Категория | Балл |
|---|---|
| Опоздание до 15 мин / 15–30 / больше 30 | −0,5 / −1 / −2 |
| Прогул · не вышел и не предупредил | −3 · −4 |
| Жалоба клиента · ошибка замера · срыв заказа | −2 · −3 · −3 |
| Грубость клиенту / серьёзное нарушение | −5 |
| Выполнил план · положительный отзыв · помог команде | +3 · +1 · +1 |

- **Повтор** той же категории нарушения в том же месяце — на балл строже.
  Поощрения повтором не усиливаются.
- **Уровень** — от суммы штрафных за месяц: 0–2 обычный контроль, 3–4 устное
  предупреждение, 5–6 письменное и план исправления, 7+ решение руководства.
  Поощрения уровень не гасят, но видны рядом. «Чистый месяц» — без нарушений.
- Сотрудник видит каждую запись в приложении и может дать **объяснение** —
  руководство видит его рядом с фактом.
- Уровень **ничего не делает сам**: система не увольняет по цифре и не
  удерживает из зарплаты. Ошибочную запись руководство удаляет; всё пишется в
  журнал действий.

## Категории швей

Три ступени, от которых зависит расценка за пошив. Категория — следствие
рейтинга, а не оценка руководителя (`packages/shared/src/constants/sewerCategory.ts`).

- **Откуда.** Балл рейтинга за **прошлый месяц** с учётом дисциплины: закрытый
  пошив — плюс, опоздание и другие записи дисциплины — минус. Пока прошлого
  месяца нет (система только запущена) — по текущему.
- **Ступени** — по доле от лидера среди швей: ≥ 80 % — 1-я, ≥ 50 % — 2-я,
  ниже — 3-я. Ноль баллов и новенькая без истории — 3-я.
- **Расценка.** Руководитель пишет ставку первой категории — за пошив 50 000;
  программа подсказывает сумму по категории назначенной швеи: 2-я — 80 %
  (40 000), 3-я — 60 % (30 000). Подставляется одной кнопкой, но остаётся
  решением руководителя: сумму можно оставить любую.
- Категория видна в выборе швеи на заказ, в таблице рейтинга, в списке
  сотрудников (панель и приложение) и швее — в её рейтинге в приложении.
- **Поправить руками.** В списке сотрудников у швеи есть выбор: «Авто» —
  расчёт по рейтингу, или 1/2/3 вручную (`users.setSewerCategory`,
  `users.sewer_category`). Ручная выше расчётной: перевод человека
  случается раньше, чем это видно по закрытым заказам.

## Отчёты

Страница «Отчёты» в панели — за выбранный месяц, всё считает сервер
(`reports.service.ts`), каждая таблица выгружается в Excel:

- **Касса по дням и способам оплаты** — приход по дням: наличные / карта /
  QR / Click, итого, возвраты; и то же по продавцам (кто принял).
- **Зарплата: из чего сложилась** — по каждому сотруднику и роли: схема,
  часы, закрытые заказы, сдельные, баллы дисциплины, категория швеи, строки
  начисления и итог. Кому условия оплаты не заданы — перечислены строкой.
- **Заказы: сроки и переделки** — закрыто / в срок / с опозданием / без
  срока, средняя просрочка, возвраты на переделку; список просроченных с
  швеёй и установщиком; по швеям — сшито, переделок, с опозданием.
- **Швеи: выработка и категория** — сшито, м², качество, сроки, балл,
  дисциплина, категория; динамика за полгода.
- **Скидки за месяц** — см. «Скидки».

## Telegram

Две независимые доставки поверх одного источника событий:

- **Личные уведомления** — то же, что приходит в приложение, дублируется в
  личку тем, кто привязал Telegram (Профиль → Уведомления в Telegram).
- **Лента действий в группу** — бот пишет в рабочую группу о каждом
  действии из журнала: кто создал заказ, сменил статус, пробил чек, выдал
  зарплату. Лента висит на `recordAudit`, поэтому новое действие попадает в
  неё само, без отдельной доработки.

Без `TELEGRAM_BOT_TOKEN` Telegram выключен целиком; без
`TELEGRAM_GROUP_CHAT_ID` работают только личные уведомления. Номер группы
бот сообщает по команде `/id`, отправленной в самой группе.

## Чего в системе нет

Не «не успели», а сознательно не придумывали за заказчика:

- **Клиенты как сущность.** Имя и телефон хранятся в заказе. Нет истории
  обращений и повторных продаж.
- **Склад тканей.** Ни остатков, ни списания при раскрое, ни порогов.
- **Воронка продаж.** Нет лидов и необорванных обращений — поэтому нет
  и конверсии: делить закрытые заказы не на что.
- **Производственный план.** Отсюда нет ни одного «выполнение %».
  `payroll_schemes.kpi_target` — план для расчёта зарплаты, а не для цеха.
- **Задачи SMM.**
- **Клиентские SMS и пуши.** Уведомления только внутренние.

Каждый из этих разделов честно сообщает в интерфейсе, чего не хватает,
вместо того чтобы показывать правдоподобные цифры.
