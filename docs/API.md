# API

tRPC поверх Hono. Единственная точка входа — `/trpc`; REST-эндпойнтов нет
намеренно: контракт задаётся типом `AppRouter`, а не документацией.

Этот файл — справочник. Почему устроено именно так — в
[ARCHITECTURE.md](./ARCHITECTURE.md), правила предметной области —
в [BUSINESS_LOGIC.md](./BUSINESS_LOGIC.md).

## Общее

**Транспорт.** `superjson`, поэтому `Date` доходит датой, а не строкой.
Тело запроса и ответа обёрнуто в `{ "json": … }`.

```
GET  /trpc/<процедура>?input=<url-encoded {"json":…}>
POST /trpc/<процедура>       тело: {"json": …}
```

**Аутентификация.** Заголовок `Authorization: Bearer <access-токен>`.
Access живёт 15 минут; продлевается через `auth.refresh`, который **ротирует**
refresh-токен. Предъявление уже отозванного refresh-токена гасит все сессии
сотрудника — это признак кражи.

**Ошибки.**

```json
{"error":{"json":{
  "message":"Заказ недоступен: вы не участвуете в его выполнении",
  "code":-32003,
  "data":{"code":"FORBIDDEN","httpStatus":403,"path":"orders.byId",
          "zodError":null,"requestId":"b1aa…"}
}}}
```

`zodError` — ошибки валидации по полям, чтобы форма подсветила нужный ввод.
Тексты русские: подключена карта сообщений Zod (`lib/zodMessages.ts`).
`requestId` совпадает с идентификатором в серверном логе.
Стек в ответ **не попадает** при `NODE_ENV=production`.

**Пагинация.** Списочные процедуры принимают `{ page, pageSize }`
(по умолчанию 1 и 20, потолок 100) и возвращают
`{ items, page, pageSize, total, totalPages }`.

**Деньги** передаются в минорных единицах (тийинах) как целые числа,
плюс отформатированная строка рядом: `revenueMinor` и `revenueFormatted`.

**Ограничения.** Пять неудачных попыток входа по одному номеру закрывают его
на 15 минут. Обращения к `auth.*` ограничены 120 в минуту с адреса — этот
предел отдаётся как HTTP 429 **до** разбора запроса как вызова процедуры,
поэтому его ответ не в формате tRPC.

## Уровни доступа

| Обозначение | Кто |
|---|---|
| публичная | без токена |
| вошедший | любой сотрудник с действующим токеном |
| участник | вошедший, участвующий в конкретном заказе; руководство — всегда |
| руководство | директор и администратор |
| директор | только директор |

Скрытие кнопок в интерфейсе — удобство. Проверяет **процедура**.

## auth

| Процедура | Тип | Доступ | Назначение |
|---|---|---|---|
| `login` | mutation | публичная | Вход по телефону и паролю |
| `refresh` | mutation | публичная | Обновление пары токенов с ротацией |
| `me` | query | вошедший | Профиль, роли, филиалы |
| `logout` | mutation | вошедший | Выход с текущего устройства |
| `logoutAll` | mutation | вошедший | Выход со всех устройств |
| `changePassword` | mutation | вошедший | Смена своего пароля; завершает все сессии |

Телефон принимается в любом виде и приводится к E.164, поэтому
`+998 90 123 45 67` и `901234567` — один сотрудник.

## orders

| Процедура | Тип | Доступ | Назначение |
|---|---|---|---|
| `list` | query | вошедший | Список с фильтрами; видны только свои заказы |
| `byId` | query | участник | Карточка с позициями и исполнителями |
| `create` | mutation | продавец, админ, директор | Создание вместе с позициями |
| `update` | mutation | руководство или автор | Правка, пока заказ не ушёл дальше проверки админом |
| `setPrice` | mutation | руководство | Сумма работ и предоплата |
| `changeStatus` | mutation | участник | Переход по таблице `ORDER_TRANSITIONS` |
| `availableTransitions` | query | участник | Действия, доступные вызывающему |
| `assign` | mutation | руководство | Назначение мастера, швеи, ОТК, установщика |
| `history` | query | участник | История переходов |
| `installationTeam` | query | участник | Бригада установки |
| `addTeamMember` / `removeTeamMember` | mutation | руководство | Состав бригады |
| `cancel` | mutation | руководство | Отмена с обязательной причиной |
| `itemsByOrderIds` | query | вошедший | Позиции пачкой — для списков |

Фильтры `list`: `status[]`, `phase`, `priority`, `branchId`, `assigneeId`,
`search` (номер, имя, телефон), `deadlineFrom` / `deadlineTo`,
`includeArchived`. По умолчанию выполненные и отменённые скрыты.

`create` принимает от 1 до 50 позиций. Размеры — строкой (`150x200`) либо
явными `widthCm` / `heightCm`; площадь считается, а не вводится.

## orderPhotos, orderComments

| Процедура | Тип | Доступ | Назначение |
|---|---|---|---|
| `orderPhotos.listByOrder` | query | участник | Галерея по стадиям |
| `orderPhotos.upload` | mutation | участник с ролью стадии | Загрузка фото |
| `orderPhotos.remove` | mutation | автор загрузки или руководство | Удаление |
| `orderComments.listByOrder` | query | участник | Лента комментариев |
| `orderComments.add` | mutation | участник | Текстовый комментарий |
| `orderComments.addVoice` | mutation | участник | Голосовой, до 300 секунд |
| `orderComments.remove` | mutation | автор или руководство | Удаление |

Файлы приходят в base64: `{ fileName, mimeType, content }`. Белые списки —
`ALLOWED_IMAGE_MIME_TYPES` и `ALLOWED_AUDIO_MIME_TYPES`, потолок размера
задаёт `MAX_UPLOAD_SIZE_MB`.

Загрузка фото стадии `install_after` **автоматически закрывает заказ**.
Ответ `upload` содержит `autoCompleted: boolean`.

Ограничений по роли на комментарии нет намеренно: швея должна прочитать
замечание установщика, а продавец — увидеть их оба.

| `checkIn` | mutation | вошедший | Открыть смену по координатам |

## users

| Процедура | Тип | Доступ | Назначение |
|---|---|---|---|
| `list`, `listByRole` | query | руководство | Списки сотрудников |
| `byId` | query | сам сотрудник или руководство | Профиль |
| `uploadAvatar`, `removeAvatar` | mutation | вошедший | Только своё фото |
| `create`, `update`, `setActive` | mutation | директор | Учётные записи |
| `grantRole`, `revokeRole` | mutation | директор | Роли |
| `resetPassword` | mutation | директор | Сброс пароля |
| `setBranches` | mutation | руководство | Привязка к филиалам |
| `stats`, `presenceToday`, `attendance`, `birthdays`, `performance` | query | руководство | Кадровая аналитика |

Ролями управляет **исключительно директор**, в том числе своими.
Сотрудники не удаляются: увольнение — это `setActive(false)`, которое
дополнительно завершает все сессии.

## payroll

| Процедура | Тип | Доступ | Назначение |
|---|---|---|---|
| `payroll.schemes.list` | query | руководство | Схемы начисления |
| `payroll.schemes.upsert` | mutation | директор | Создание и правка схемы |
| `payroll.calculate` | mutation | руководство | Расчёт за период — черновики |
| `payroll.list` | query | руководство | Расчёты за период |
| `payroll.approve` | mutation | директор | Утверждение; сумма фиксируется |
| `payroll.markPaid` | mutation | директор | Отметка о выплате |
| `payroll.my` | query | вошедший | Свои расчёты за год |

Схемы вынесены в подроутер `schemes`, сами расчёты лежат на верхнем уровне
`payroll`. Уже утверждённые записи `calculate` пропускает и возвращает их
число отдельно — чтобы в интерфейсе было видно, что часть ведомости
не пересчитывалась.

Схема привязана к **роли**, а не к сотруднику. Пересчёт возможен только
пока запись в статусе черновика.

## purchases, catalog, branches

| Процедура | Тип | Доступ | Назначение |
|---|---|---|---|
| `purchases.items.*` | query/mutation | список — вошедший, правка — руководство | Каталог закупочных товаров |
| `purchases.listByOrder` | query | участник | Закупки по заказу |
| `purchases.create` / `remove` | mutation | руководство | Закупка по заказу |
| `purchases.orderCost` | query | участник | Себестоимость; выручка и маржа — только руководству |
| `catalog.*` | query/mutation | список — вошедший, правка — руководство | Справочники: модели, материалы, цвета, карнизы, тюль, сачак, аксессуары |
| `branches.*` | query/mutation | список — вошедший, правка — руководство | Филиалы и радиус чек-ина |

`orderCost` возвращает рядовому сотруднику закупки, но `null` вместо выручки,
маржи и рентабельности: сколько мастерская заработала на клиенте —
управленческая цифра.

## reports

Все — только руководству.

| Процедура | Назначение |
|---|---|
| `dashboard` | Верхние показатели, счётчики статусов, этапы конвейера |
| `workshops` | Швейный цех и участок установки, объём в м² |
| `installationQueue` | Очередь на установку по срочности |
| `topPerformers` | Лучший в каждой роли: выручка, метраж, срок, качество |
| `attention` | Просрочки и очереди, требующие вмешательства |
| `topProducts` | Самые продаваемые модели за месяц |
| `dynamics` | Динамика заказов и выручки по дням |
| `sellerRating` | Рейтинг продавцов |
| `payrollFund` | Фонд зарплаты по месяцам |
| `ordersByPhase` | Распределение заказов по фазам |
| `finance` | Финансовый итог месяца |
| `employeePerformance` | Выработка сотрудников |

Все принимают необязательный `branchId`.

**Чего в отчётах нет и почему:** конверсии продавца (нет лидов
и необорванных обращений), остатков ткани (нет складского учёта), процента
выполнения плана (нет производственного плана как сущности). Цифра, которой
неоткуда взяться, опаснее её отсутствия.

## Раздача файлов

```
GET /files/<ключ>?expires=<unix>&sig=<hmac>
```

Не процедура tRPC, а статическая раздача при `STORAGE_DRIVER=disk`.
Ссылку выдаёт `getUrl()` на каждый запрос заново, срок — час. Без подписи
или с истёкшим сроком — `403`, одинаково для существующих и отсутствующих
файлов.

При `STORAGE_DRIVER=s3` файлы отдаёт сам бакет по подписанной ссылке,
Node-процесс в этом не участвует.
