# Выпуск 3 «Заказы» — дизайн

Дата: 25.10.2026 · Статус: части 1–2 согласованы в чате, часть 3 решена
исполнителем по поручению «делай до конца»

## 1. Зачем

Заказчик прислал семь правок (переписка 24–25.10). Они разбиты на три
выпуска: «Заказы» (этот), «Зарплата», «Табло». Сюда вошли пять пунктов —
ежедневная работа с заказами и две настоящие ошибки.

| № | Что сказал заказчик | Что делаем |
|---|---|---|
| 1 | «текущий исполнитель» — в списке заказов (сайт) и в карточке (приложение) | колонка и строка с исполнителем текущего этапа |
| 2 | «изменения заказа внутри заказа, web/app» — карандаш в шапке | правка заказа со страницы заказа |
| 3 | «поисковик в приложении, фильтр по статусу/исполнителю» | поиск и фильтры на экране «Работа» |
| 4 | «до получения остатка закрыть заказ нельзя» | закрытие только при остатке ≤ 0 |
| 6 | «система не должна обновлять роли автоматически, менять может только директор» | назначать только тех, у кого роль уже есть |

### Решения заказчика (через исполнителя, 25.10)

- Порядок выпусков: Заказы → Зарплата → Табло.
- Долг после установки: заказ ждёт оплаты в «Установка завершена» и
  **закрывается сам**, когда остаток стал 0.
- Старые закрытые заказы с долгом (как DH-000028) **остаются закрытыми**;
  нужен фильтр «С долгом».
- Роли, уже выданные системой: **показать директору список**, снимает сам.
- Готовые шторы без установки: **только полная оплата**.
- Править заказ: директор, админ, менеджер — любой открытый заказ; продавец —
  свой заказ, пока админ его не принял.

### Что считаем успехом

1. Ни одним путём (кнопка, массовое действие, фото, продажа готовых) заказ с
   остатком > 0 не попадает в «Выполнен».
2. Назначение на заказ никогда не меняет роли сотрудника.
3. Исполнитель в списке на сайте и в приложении считается одним правилом из
   `packages/shared`.
4. В приложении можно найти заказ по номеру, клиенту, телефону и отобрать по
   статусу и исполнителю; список не обрывается на 50-м заказе.
5. Заказ правится со страницы заказа на сайте и в приложении, а текущий
   исполнитель узнаёт о правке.

## 2. Часть 1 — роли и долги (сервер)

### 2.1 Роли (п. 6)

Причина бага — `ensureUserHasRole` в `apps/api/src/services/orderWorkflow.service.ts`:
при назначении на заказ он молча выдавал роль. Через назначение админ и
менеджер фактически раздавали роли, хотя по ТЗ (п. 1.3) их меняет только CEO.

- `ensureUserHasRole` заменяется на `assertAssignableExecutor`: сотрудник
  существует, активен **и уже имеет роль этапа**. Иначе `BAD_REQUEST`:
  «У сотрудника нет роли «Установщик». Роли меняет директор». Вставки в
  `user_roles`, аудита `user.role_granted` и уведомления о роли больше нет.
- Путь один — `assignExecutor`, через него идут `orders.assign`,
  `changeStatus`/`changeStatusBatch` с `assigneeId`.
- Сайт (`useAssigneeCandidates`) и приложение (`OrderManagement`): в выборе
  исполнителя только люди с ролью этапа; «Ещё сотрудники» / «Ещё» убираются.
- **Список для директора.** Новая процедура `users.autoGrantedRoles`
  (`ceoProcedure`): роли, выданные через назначение (`audit_log`:
  `user.role_granted` с `details.viaOrderAssignment = true`) и всё ещё
  действующие (есть строка в `user_roles`). Поля: сотрудник, роль, когда
  выдана, кто назначал. На странице «Сотрудники» — блок «Роли, выданные
  системой автоматически» только для CEO, с кнопкой «Снять роль»
  (существующая `users.revokeRole`). Пустой список — блока нет.
- Комментарии, которые утверждали «роль выдаст сам API» (веб, приложение,
  `smoke.ts`), и подпись `viaOrderAssignment` в журнале остаются только
  там, где описывают историю.

### 2.2 Долги (п. 4)

Отдельного статуса «Ждёт оплаты» нет: он задел бы все экраны, фильтры и
отчёты. Заказ в `installation_done` с остатком > 0 и есть «ждёт оплаты».

**Правило** (`packages/shared`): `closeBlockedByDebt(order)` — для типов
`custom` и `ready_made` закрыть нельзя, пока `remainingPayment > 0`. Пошив на
склад (`stock`) правилом не затронут: цена 0.

**Где проверяется.** В `changeOrderStatus` — единственной точке, через
которую проходит любое закрытие: при `toStatus = completed` и долге —
`CONFLICT` «Остаток 800 000 сум — сначала примите оплату». Остаток читается
из заказа, загруженного под блокировкой, то есть уже с последними
проводками той же транзакции.

**Пути закрытия:**

1. «Закрыть заказ» вручную (`installation_done → completed`): кнопка на
   сайте и в приложении неактивна с подсказкой про остаток; сервер откажет.
   Массовое закрытие пропускает должников и показывает причину по каждому
   (как сейчас для прочих ошибок пакета).
2. Фото «после установки»: `autoCompleteIfInstallFinished` доводит заказ до
   `installation_done` и **останавливается**, если остаток > 0. Фото
   сохраняется, ошибки нет. Подсказки клиентов «фото закроет заказ»
   меняются на «…закроет заказ, если он оплачен» — без сумм (цех денег не видит).
3. **Закрытие по оплате.** Новая `closeIfSettled(executor, orderId, actor)` в
   `orderWorkflow.service.ts`: заказ в `installation_done`, остаток ≤ 0 →
   `completed` с комментарием «Оплата получена полностью — заказ закрыт
   автоматически». Вызывается после `payments.acceptForOrder`, после
   `orders.setPrice` и после правки цены в `orders.update`. Права на само
   действие уже проверены вызывающей процедурой (принять оплату может
   продавец заказа, установщик или руководство), поэтому этот системный
   переход не проверяет закрепление этапа за установщиком — иначе продавец,
   принявший последний платёж, получил бы FORBIDDEN.
4. Готовые шторы без установки (`sellReadyMade`, `needsInstallation=false`,
   `needsRework=false`): `deposit` должен равняться цене со скидкой. Иначе
   `BAD_REQUEST` «Без установки готовые шторы продаются только при полной
   оплате». Форма продажи на сайте и в приложении подставляет полную сумму и
   не даёт отправить меньше. Продажа с установкой или переделкой — по общему
   правилу.

**Пометка «Ждёт оплаты».** `installation_done` + остаток > 0: на сайте и в
приложении рядом со статусом — бейдж «Ждёт оплаты» для тех, кому
`maskStageFees` отдаёт деньги клиента. Цех видит только статус.

**Побочные эффекты.** Процент/KPI продавца и рейтинг считаются по закрытию —
теперь они приходят, когда получены деньги. Отчёт «Сроки и опоздания»
считает опоздание от **даты завершения установки** (последняя запись
`installation_done` в `order_status_history`), а для заказов без установки —
от `completed_at`; месяц отчёта по-прежнему по `completed_at`.

**Старые закрытые с долгом** не трогаются. Фильтр «С долгом» (`withDebt`):
статус `installation_done` или `completed` и остаток > 0. Доступен ролям,
которые видят деньги клиента; остальным `FORBIDDEN`. Сайт: вкладка
«С долгом» на странице заказов. Приложение: пункт в фильтре статуса.

**Документы.** `docs/REQUIREMENTS.md` п. 3.9 и `docs/BUSINESS_LOGIC.md`
«Автозакрытие» переписываются под новое правило.

## 3. Часть 2 — исполнитель и поиск

### 3.1 Текущий исполнитель (п. 1)

`STATUS_OWNER` переезжает из `orderWorkflow.service.ts` в
`packages/shared` как `ORDER_STATUS_OWNER` + `currentExecutorRole(status)`;
сервер продолжает пользоваться им для прав и уведомлений.

| Статусы | Роль |
|---|---|
| `measurement_assigned`, `measurement_done` | мастер |
| `pending_sewing_assignment`, `sewing_in_progress`, `sewing_done` | швея |
| `pending_qc`, `qc_failed`, `qc_passed` | контролёр |
| `pending_installation_assignment` … `installation_done` | установщик |
| `new`, `pending_admin_review`, `rejected_to_ceo`, `completed`, `cancelled` | — |

`orders.list` отдаёт у каждой строки
`currentExecutor: { role, userId, fullName } | null`: `null` — у статуса
нет исполнителя; `userId = null` — этап есть, человек не назначен. Имена
всей страницы — одним запросом `users where id in (…)`.

- **Сайт**, `OrdersView`: колонка «Исполнитель» после «Статус» — имя и
  мелко роль; серое «не назначен»; «—», если исполнителя нет.
- **Приложение**, `OrderCard`: имя под бейджем статуса (выделено, как на
  скриншоте заказчика); серое «не назначен»; ничего, если исполнителя нет.
- Карниз параллелен основной цепочке и в колонке не показывается.

### 3.2 Поиск в приложении (п. 3)

`WorkScreen`, вкладки «В работе», «Просрочены», «Все»; под быстрыми кнопками:

- Поле «Номер, клиент или телефон» → `orders.list.search`, задержка 300 мс.
- Ряд фильтров:
  - «Статус» — шторка со статусами по этапам (замер, пошив, контроль,
    установка, закрыт) + «С долгом» для видящих деньги;
  - «Исполнитель» — шторка со списком сотрудников (`users.assignable`) и
    поиском по имени; только директор, админ, менеджер
    (`useCanDispatchOrders`).
  - Выбранное — чипами с крестиком, рядом «Сбросить».
- Сервер: фильтр `assigneeId` учитывает и `corniceInstallerId`.
- Список подгружается страницами при прокрутке вместо одной страницы на 50.
- «Просрочены» отбирает сервер: новый параметр `overdue` (срок раньше
  сегодняшнего дня по Ташкенту, статус активный по `isActiveStatus`) вместо
  фильтра на телефоне по первым 50.

## 4. Часть 3 — правка заказа (п. 2)

Решено исполнителем; сервер уже умел почти всё (`orders.update`), но ни сайт,
ни приложение его не вызывали.

### 4.1 Права — одно правило в `packages/shared`

`canEditOrder(order, user)`:
- директор, админ, менеджер — любой заказ, кроме `completed`/`cancelled`;
- автор — свой заказ в `new`, `pending_admin_review`, `rejected_to_ceo`;
- остальные — нет.

Сервер (`orders.update`) переходит на это правило: закрытые и отменённые
заказы больше не правятся никем (раньше руководство могло). Клиенты по нему
же показывают карандаш.

### 4.2 Что правится

Клиент, телефон, пожелания клиента, адрес установки с координатами, срок,
приоритет, позиции, **цена и скидка**. Не правятся: филиал, тип заказа,
предоплата (это проводки), расценки этапов (отдельная кнопка «Расценки»).

- **Цена** добавляется во вход `orders.update` (`workPrice`,
  `discountAmount`, `discountReason`) — по общему правилу прав, иначе
  продавец не смог бы исправить цену до принятия. Изменение пишет тот же
  аудит `order.price_changed`, что и `setPrice`, и вызывает `closeIfSettled`.
  `setPrice` остаётся для панели управления; закрытые заказы отклоняет так же.
- **Позиции** — полная замена, как сейчас. Форма правки получает позиции
  целиком и возвращает их с метражом, проставленным админом, — метраж не
  теряется. Если в форме изменён код материала, метраж этого материала
  сбрасывается в `null`: старые метры к новой ткани не относятся.
- **Готовые шторы** (`ready_made`): позиции не правятся — товар уже списан
  со склада; сервер отклоняет `items` с понятной ошибкой, форма прячет раздел.
- **Пошив на склад** (`stock`): клиент и цена в форме скрыты (клиент —
  мастерская, цена 0).

### 4.3 Кто узнаёт о правке

Новое уведомление `order_updated` текущему исполнителю (по правилу 3.1),
если он назначен и правил не он сам: «Заказ DH-000186 изменён: позиции,
срок». Тон — info, ведёт на заказ. Значение перечисления добавляется
миграцией (`ADD VALUE IF NOT EXISTS`), как в выпуске 2.

### 4.4 Интерфейс

- **Сайт**: кнопка-карандаш «Изменить» в шапке страницы заказа → диалог с
  теми же полями, что у создания. Поля формы выносятся из
  `OrderCreateDialog` в общий компонент, создание и правка используют его.
  Отправляются только изменённые поля.
- **Приложение**: карандаш в шапке экрана заказа (`headerRight`) → экран
  «Изменить заказ» на тех же компонентах, что `OrderCreateScreen`.

## 5. Проверки

- `packages/shared` (Vitest): `currentExecutorRole`, `canEditOrder`,
  `closeBlockedByDebt`, сброс метража при смене кода.
- `apps/api` (Vitest): чистые части новых сервисов.
- `apps/api/src/scripts/smoke.ts` на живой базе:
  - назначение без роли → ошибка, роль не появилась;
  - `autoGrantedRoles` видит старую автовыдачу;
  - закрыть с долгом → ошибка; массовое закрытие пропускает должника;
  - фото «после установки» с долгом → `installation_done`, фото сохранено;
  - последний платёж → заказ закрыт; снижение цены до оплаченного → закрыт;
  - готовые без установки с неполной оплатой → ошибка;
  - `list`: `currentExecutor`, `withDebt` (и `FORBIDDEN` для цеха),
    `overdue`, `assigneeId` по карнизчику;
  - `update`: закрытый → ошибка; продавец после принятия → ошибка; цена →
    аудит; готовые с `items` → ошибка; уведомление `order_updated`.
- Сайт и приложение: `typecheck`, `lint`; снимки Playwright ключевых экранов.

## 6. Выкатка

- Миграция: значение `order_updated` в перечислении уведомлений.
- Нужен **новый APK** для всех ролей: поиск, исполнитель, правка, подсказки
  про оплату. Приложения выпуска 2 переживут новое уведомление (запасной тон),
  более старые — нет.
